# DevFest Hackathon 2026 — 参加・開発ルール

このOrganizationは、DevFest Hackathon 2026のチーム開発に使用します。全員が「毎日、main上で動く1本のプロダクトを更新する」ことを最優先にします。

## 提出時の必須事項

- 運営から招待された提出用リポジトリは **公開（Public）** です。開催中も運営・審査員・ほかの参加者が閲覧できます。
- GitHubから届いた招待は **7日以内** に受け入れてください。期限切れやメンバー変更があった場合は、すぐに運営へ連絡してください。
- 審査対象は、 **提出期限までに提出用リポジトリへ置かれたコードと資料のみ** です。
- デプロイ済みの作品がある場合は、提出用リポジトリのREADMEにURLを記載してください。
- 提出期限後は提出用リポジトリが読み取り専用になり、pushできません。
- 提出用リポジトリではGitHub ActionsとGitHub Pagesを利用できません。必要な場合は、このOrganizationに開発用リポジトリを作成してください。

## 1. 完成の定義

- 個人のブランチで動くだけでは未完成です。 **mainへ統合され、代表ユーザーフローが通る状態** を完成とします。
- North Star Demoは「4人が参加し、別々のパーツを作り、完了を同期し、最後に合体させる」体験です。
- 実装判断は常に「この作業が11月10日のデモで、4人の共同制作体験を強くするか」で決めます。

### 優先順位

- **P0（絶対に削らない）:** 4人参加、別パーツ表示、リアルタイム完了同期、最後の合体
- **P1（P0完成後）:** Gemini材料認識、AIヘルプ、日英切替、テスト強化
- **P2（余裕がある場合）:** 完成カードの装飾、推薦説明の高度化、追加作品、UI装飾

P0が不安定な間は、P1・P2の新規実装を開始しません。

## 2. 4人の役割

初日の30分で経験を確認し、A〜Dを実名へ割り当てます。全員がPrimaryとSecondaryの両方を持ちます。

| 役割 | Primary責務 | バックアップ |
|---|---|---|
| A: Tech Lead / Firebase | Firestore、Auth、Functions、Security Rules、デプロイ | DのQA・障害解析 |
| B: Frontend / Workshop UX | React画面、QR参加、制作画面、リアルタイムUI | Cのコンテンツ実装 |
| C: AI / Content | Gemini、材料認識、作品推薦、日英手順、作品データ | BのUI実装 |
| D: Integration / QA / Product | E2E、統合、テスト、README、デモ、提出物 | AのFunctions実装 |

- AとD、BとCを相互バックアップのペアにします。
- Dは「統合できない機能は完成していない」と判定できます。
- 1人が半日不在ならその日のP1を停止し、終日不在なら新機能を増やしません。

## 3. Git・PRルール

- `main`への直接pushは禁止します。
- ブランチ名は `feat/...`、`fix/...`、`test/...`、`docs/...` のいずれかにします。
- feature branchは原則半日以内で削除できる大きさにします。
- 1 PRは1目的、生成物を除き原則250変更行以下を目安にします。
- Draft PRを早めに作り、設計や統合のずれを先に共有します。
- 通常PRは1人の承認が必要です。Firestore schema、Security Rules、Auth、Functionsの権限変更はAの承認を必須とします。
- AI生成コードも、人間が全行を読み、必要なテストを通してからmergeします。
- mergeはsquashを使い、merge直後にPreviewまたはEmulatorで確認します。

### PRの完了条件

- 目的と変更理由がPR本文に書かれている
- 関係するテストが通っている
- 秘密情報や不要な生成物を含んでいない
- UI変更はスマートフォンで確認している
- 関係するE2Eがmain上で動く

## 4. AI利用ルール

1. AI生成物はcommit前に人間が読み、正確性・セキュリティ・保守性を確認します。
2. 1プロンプト1タスクとし、同じタスクを複数人が重複してAIへ依頼しません。
3. production promptはGit管理し、変更を通常のPRでレビューします。
4. APIキー、個人情報、未公開の秘密情報をAIへ貼り付けません。
5. 「AIが提案したから」は採用理由にしません。候補、利点・欠点、採用理由を人間が記録します。
6. Geminiは画像や自然言語の構造化を担当し、権限、人数条件、工程依存、制作可否は決定論的なコードで判定します。
7. 翻訳、工作手順、安全表現、Gemini出力は担当者が必ず目視確認します。

## 5. コミュニケーションと意思決定

進捗共有は `Done / Next / Blocker` の3項目だけにします。

| タイミング | 時間 | 内容 |
|---|---:|---|
| 開始時 | 10分 | 今日必ず完成させる1ゴール |
| 昼 | 5分 | Blockerのみ共有 |
| 17時頃 | 15分 | main統合、4端末確認、90秒デモ |
| 終了前 | 10分 | 明日のP0とDecision Log |

- 可逆的な判断は15分で打ち切り、担当DRIが決定します。
- Firestore schema、認証、AI呼び出し境界など戻しにくい判断は30分以内にAと関係者1名で決めます。
- 30分詰まったらAIで原因候補を3つ出し、バックアップ担当へ相談します。さらに30分で解決しなければ仕様を縮小または代替案へ切り替えます。

Decision Logは次の5行だけ残します。

```text
Decision:
Why:
Alternatives:
Why rejected:
Owner:
```

## 6. 品質・セキュリティ

最低限、次のP0ケースをデモ前に確認します。

- 主催者がroomを作成できる
- 4人がQR参加し、同じ状態を見られる
- 5人目は拒否される
- 全端末へ同じ作品と担当パーツが反映される
- 自分の工程完了が即時同期される
- dependency未完了の工程は完了できない
- 全パーツ完了後だけAssemblyが表示される
- 完成承認でcompletedになる
- 未認証ユーザーの操作は拒否される

秘密情報は `.env` や `.dev.vars` に保存し、`.gitignore` の対象にします。誤って公開した場合は履歴から消すだけで済ませず、直ちにキーを無効化・再発行して運営へ連絡します。

## 7. 5日間のFreeze基準

- **11/5:** 仮データでも4端末の最小E2Eをmainで通す
- **11/6:** 4パーツ割当、工程表示、完了同期、合体解放を完成させる
- **11/7:** Gemini、日英切替、合体体験を統合する
- **11/8:** 新機能を止め、実物ワークショップとP0テストで壊す
- **11/9:** Release Candidate、README、動画、アーキテクチャ図、提出資料を固定する。午後からmainへ新機能を入れない
- **11/10:** デモリハーサルと最終確認を行い、19:00より前に提出する

問題が起きた場合は、完成カードの装飾 → AI Helpの高度化 → 推薦説明 → 追加作品 → 材料認識の順に削ります。P0の4人共同制作体験は削りません。
