# Co-Make

> **それぞれの「つくる」が、ひとつになる。**

知識も、言葉も、経験も違う。それでも一緒に作れる。

Co-Makeは、学校や地域の対面ワークショップで、2〜4人が異なるパーツを制作し、最後に組み合わせて1つの作品を完成させるためのWebアプリケーションです。

Geminiによる材料認識・作品推薦と、Firebaseによるリアルタイム進捗共有を活用し、言語や工作経験の違いを超えた共同制作を支援します。

### コンセプト

**AIが作品を作るのではなく、AIが人間同士の共同制作を支える。**

参加者は異なるパーツを担当し、写真付きの手順を見ながら制作します。各パーツが完成したら全員で持ち寄り、物理的に組み合わせて1つの作品を完成させます。アプリの操作よりも、現実の共同制作体験を主役にします。

## 解決したい課題

対面ワークショップには、次のような課題があると考えています。

1. 言語や制作経験の違いによって、手順を理解しにくい
2. 工作経験のある参加者に作業が集中しやすい
3. 手元の材料で何を作れるのか判断しづらい
4. 困ったときに質問や相談をしにくい
5. 個別作業だけでは、共同制作の実感が生まれにくい

Co-Makeは、材料認識・作品選択・工程分担・制作支援・進捗共有を一貫した体験として提供します。

> これらは現時点の課題仮説です。効果は実機テストと利用者検証によって確認します。

## ユーザー体験

1. **集まる** — 主催者がルームを作成し、参加者がQRコードから参加する
2. **材料を確認する** — 材料を撮影し、Geminiの認識結果を参加者が確認・修正する
3. **作品を選ぶ** — 検証済みの作品から候補を比較し、主催者が決定する
4. **担当を決める** — 各参加者へ異なるパーツと工程を割り当てる
5. **それぞれ制作する** — 日英の写真付き手順を見ながら制作し、完了を同期する
6. **全員で組み立てる** — 全パーツ完成後に持ち寄り、物理的に合体させる
7. **完成を記録する** — 完成写真と各自の貢献をカードとして保存する

### 体験設計の原則

- スマートフォンの操作時間を短くする
- 参加者全員に実際の制作機会を設ける
- 可能な工程は並行して進める
- 自分の担当が全体のどこにつながるかを見せる
- 最後の共同組み立てを体験の中心にする

## 技術スタック

| 領域 | 技術 | 用途 |
|---|---|---|
| Frontend | React / TypeScript / Vite | UI・型安全な共同開発 |
| Styling | Tailwind CSS | スマートフォン中心のUI |
| Authentication | Firebase Authentication | 匿名認証 |
| Database | Cloud Firestore | 共有データ・リアルタイム同期 |
| Backend | Cloud Functions for Firebase | 認可・整合性・AI連携 |
| Storage | Cloud Storage for Firebase | 必要な画像の保存 |
| Hosting | Firebase Hosting | アプリ公開 |
| AI | Gemini API | 材料認識・推薦・質問回答 |
| Validation | Zod | AI・APIデータ検証 |
| i18n | react-i18next | 日英表示 |
| Test | Vitest / Firebase Emulator | ロジック・認可の検証 |

### 技術選定の方針

- 主要言語をTypeScriptへ統一する
- Gemini APIはCloud Functions経由で呼び出し、APIキーをクライアントへ公開しない
- Firestoreへの重要な更新はサーバー側で認可・検証する
- Geminiの出力はスキーマで検証する
- 不必要なフレームワークやインフラを増やさない
- 5日間で統合・テストできる構成を優先する

## システムとAIの責務

### フロントエンド

主催者・参加者UI、写真選択、候補・工程表示、Firestore購読、Functions呼び出し、完成カードの描画を担当します。

### Firebase / Google Cloud

匿名認証、ルーム参加、材料・作品・担当の確定、工程完了時の権限・依存関係チェック、Gemini API呼び出し、データ削除を担当します。

### Gemini

1. 材料写真から材料候補を構造化する
2. ユーザーの希望を解釈し、検証済み作品の推薦理由を示す
3. 現在の工程について質問に答える
4. 仲間への質問を必要に応じて翻訳する

**制作可否、人数条件、工程依存、担当、権限は、事前に検証したテンプレートと決定的なコードで判定します。**

## チーム構成

| メンバー | 役割 | 主な担当 |
|---|---|---|
| A | Tech Lead / Frontend基盤 | 共通設計、React基盤、主催者UI、レビュー、統合、デプロイ |
| B | Firebase / Backend | Auth、Firestore、Functions、Security Rules、データ削除 |
| C | Gemini / Product Logic | AI、推薦、工程割当、作品テンプレート |
| D | Participant UI | QR参加、工程表示、進捗、ヘルプ、日英UI、スマートフォン確認 |

Aは全員のコードを代わりに書くのではなく、4人が並行開発できる基盤と境界を整えます。全員で作品の試作、手順写真、日英確認、4台実機テスト、デモと提出物の確認を行います。

## 共同開発ルール

### Git・Pull Request

- `main`は常に動作する状態を維持し、直接pushしない
- `feature/...`、`fix/...`、`test/...`、`docs/...` の短命ブランチを使う
- 1 PRは1目的、生成物を除き原則250変更行以下を目安にする
- Draft PRを早めに作り、設計やAPIのずれを共有する
- 通常PRは他のメンバー1人がレビューする
- 共通型、API、DBスキーマ、認証・認可の変更は全員へ共有する
- AI生成コードも人間が読み、動作と安全性を説明できる状態でmergeする
- squash merge後、PreviewまたはEmulatorで確認する

### AI利用

1. 1プロンプト1タスクとし、同じタスクを複数人が重複して依頼しない
2. production promptをGit管理し、コードと同様にレビューする
3. AIへAPIキー、個人情報、未公開の秘密情報を貼らない
4. AIへ独自のFirestore構造や技術スタックを勝手に追加させない
5. 「AIが提案したから」を採用理由にせず、候補と判断理由を記録する
6. 翻訳、工作手順、安全表現、Gemini出力は担当者が目視確認する

### 完成の定義

個人のブランチで動くだけでは未完成です。 **mainへ統合され、4台のスマートフォンと実物を使った通し体験が成功した状態** を完成とします。

## 意思決定と進捗共有

進捗共有は `Done / Next / Blocker` の3項目だけにします。

| タイミング | 時間 | 内容 |
|---|---:|---|
| 開始時 | 10分 | 今日必ず完成させる1ゴール |
| 昼 | 5分 | Blockerのみ共有 |
| 17時頃 | 15分 | main統合、4端末確認、90秒デモ |
| 終了前 | 10分 | 翌日のP0とDecision Log |

- 可逆的な判断は15分で打ち切り、担当者が決める
- スキーマ、認証、AI境界など戻しにくい判断は30分以内にTech Leadと関係者が決める
- 30分詰まったらバックアップ担当へ相談し、さらに30分で解決しなければ仕様を縮小する

```text
Decision:
Why:
Alternatives:
Why rejected:
Owner:
```

| 11/8 | 制作支援・完成 | 代表作品で最初から完成まで通せる。新機能を止める |
| 11/9 | 実物E2E・デモ準備 | Release Candidate、動画、README、提出資料を固定する |
| 11/10 | 最終確認・提出 | 新機能を追加せず、19:00より前に提出する |

問題が起きた場合は、完成カードの装飾 → AI Helpの高度化 → 推薦説明 → 追加作品 → 材料認識の順に削ります。4人参加、別パーツ表示、リアルタイム完了、最後の合体は削りません。

## テストとセキュリティ

最低限、次をデモ前に確認します。

- 2〜4人が同じルームへ参加し、5人目は拒否される
- 受付終了後に新規参加できない
- 材料認識結果を確認・修正できる
- 全端末へ同じ作品と担当パーツが反映される
- 他人の工程や前提未完了の工程を完了できない
- 工程完了が全端末へ即時同期される
- 全パーツ完成後だけ合体案内が表示される
- 主催者だけが完成を承認できる
- Geminiの不完全な出力を安全に扱える
- 完成後7日で関連データを削除できる

APIキー、パスワード、サービスアカウント鍵をcommitしません。秘密情報は `.env` や `.dev.vars` に置き、`.gitignore` の対象にします。誤って公開した場合は、直ちにキーを無効化・再発行して運営へ連絡します。

**デモの中心は、4人が作った別々のパーツが1つになる瞬間です。**

## 提出時の必須事項

- 運営から招待された提出用リポジトリは **公開（Public）** です
- GitHubの招待は7日以内に受け入れ、期限切れやメンバー変更は運営へ連絡します
- 審査対象は提出期限までに提出用リポジトリへ置いたコードと資料だけです
- 提出用リポジトリではGitHub ActionsとGitHub Pagesを利用できません。CI・デプロイには別の開発用リポジトリを使います
- デプロイ済み作品のURLを提出用READMEへ記載します
- 開発用リポジトリだけにある内容は審査対象にならないため、期限までに最終版を反映します
- 提出期限後は読み取り専用になり、pushできません
